# Git 改动规范审查与修复

该 skill 在独立 subagent 上下文中运行，用于对当前工作区的 git 改动做第二遍规范复核。它不依赖主会话上下文，因此必须自己读取规范、确认 diff、判断允许修改边界，并在发现不符合项时做最小修复。

核心目标：让当前 git 改动符合项目规范、用户偏好和个人开发习惯，同时避免借审查之名扩大改动范围。

## 运行上下文

本 skill 使用 `context: fork`：

- 当前 `SKILL.md` 内容会作为隔离 subagent 的执行指令
- 不要假设能看到主会话里的讨论、计划或实现理由
- 只能基于文件内容、git 状态和 diff 判断本次改动
- 完成后把审查结果、修正项和仍需用户决策的问题汇报给主会话

如果用户的原始请求包含额外约束，以用户请求为准；如果 fork 上下文中看不到这些约束，则不要猜测，只按当前规范和 diff 执行。

## 规范来源

本 skill 使用 `context: fork` + `agent: general-purpose`，fork 子代理已自动加载各级 CLAUDE.md 和无 paths 限定的 rules。审查时以已加载到上下文中的规范为主要判断依据，无需重新读取。

仅需补充读取以下懒加载内容：

- **子目录 CLAUDE.md**：当 diff 涉及特定子目录时，读取该子目录中的 `CLAUDE.md` / `CLAUDE.local.md`
- **paths 限定的 rules**：读取 `.claude/rules/` 中 `paths` 字段匹配本次改动文件的规则文件

如果找不到任何 CLAUDE.md 或规则文件，仅按本 skill 的通用原则审查，并在报告中说明。

## 工作流程

### 确认工作区状态

先获取当前 git 状态和 diff 概览：

```bash
git status --short && git diff --stat && git diff --cached --stat
```

再读取完整改动：

```bash
git diff && git diff --cached
```

审查对象包括：

- unstaged changes
- staged changes
- untracked files 中与本次任务明显相关的文件

如果存在大量 untracked 文件，先判断是否属于本次任务；不确定时只报告，不修改。

### 建立允许修改边界

只允许修改已经出现在 git diff 中的文件，或本次改动新增的文件。

允许的修改包括：

- 修正新增或已改代码中的规范违规
- 调整新增代码中的编码风格、命名、注释、结构等规范问题
- 移除本次改动引入的禁用写法
- 补充本次新增代码块的必要注释（遵循项目及个人注释偏好）
- 修正本次改动造成的不符合项目规范的问题

禁止的修改包括：

- 格式化整文件或格式化无逻辑变动的旧代码
- 借审查之名重构未改动代码
- 修改与当前 diff 无关的历史问题
- 新增测试、文档或大范围抽象，除非用户明确要求
- 执行 `git add`、`git commit`、`git reset`、`git checkout --`、`git clean` 等改变版本控制状态或破坏性命令

如果必须改未出现在 diff 中的文件才能修复问题，停止扩大修改，只在最终报告中说明原因。

### 读取必要实现

审查涉及业务逻辑时，必须读取实际实现代码，不能只凭函数名、参数名或注释判断。

- 审查对象是接口/抽象类/协议定义时，继续读取其具体实现
- 审查对象是 ORM/数据访问层调用时，继续读取对应的 SQL 或数据库操作定义
- 遇到转换、校验、状态流转、金额、权限、订单、第三方交互等敏感业务逻辑，读取完整实现后再判断
- 如果相关实现不在当前 diff 中，只读不改；发现历史问题时仅报告

### 审查重点

以读取到的 CLAUDE.md 为准，不在本 skill 中重复维护完整项目规范。审查时优先关注当前 diff 中最容易被遗漏、且违反后影响较大的问题：

- 项目规范明确禁用的写法是否被本次改动引入
- 当前改动是否破坏既有项目架构分层、模块划分、目录结构等约定
- 代码风格、命名规范、注释格式是否符合对应规范，尤其是本次新增文件和新增代码块
- 是否存在无关格式化、扩大重构、修改历史问题等超出当前 diff 的行为
- 涉及状态、金额、权限、订单、第三方交互、数据库写入等敏感逻辑时，是否已读取实际实现并保留必要注释
- 是否存在需要用户确认的歧义，尤其是修改范围、业务含义、公共组件影响或敏感业务规则

## 修改原则

发现问题后，优先做最小修复：

- 只改违规的新增/变更行及其必要上下文
- 保持原文件风格、缩进和空行
- 不引入额外抽象
- 不为理论上的未来场景增加兼容逻辑
- 不改动与本次 diff 无关的旧问题

如果问题只存在于未改动的历史代码中，不修复，只在报告中说明“历史问题，未改动”。

## 输出格式

完成后用中文汇报：

```markdown
老板，规范审查完成。

## 已修正
- `路径:行号`：修正内容与依据

## 未修改但需注意
- `路径:行号`：原因，例如属于历史代码、超出当前 git 改动范围、需要用户确认

## 未发现问题
- 如果没有发现或无需修改，说明当前 git 改动符合已读取的项目规范和用户偏好
```

如果实际没有修改，省略“已修正”或写“无”。如果存在需要用户决策的问题，不要擅自处理，在“未修改但需注意”中说明。
