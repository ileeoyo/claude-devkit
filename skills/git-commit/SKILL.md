# Git Commit 助手

分析当前Git项目的代码改动，生成规范的 commit message，经用户确认后执行提交。

## 规则速览

整个流程围绕三条铁则展开：

- **范围明确**：提交前必须先定清单——哪些提交、哪些忽略、为什么
- **分析精准**：message 只反映"本次要提交的文件"的改动；忽略的文件不写入
- **展示先于授权**：请求提交授权前，必须先完整展示提交文件范围、忽略文件范围和 commit message
- **授权前置**：未经用户确认绝不执行 `git commit`

commit message 格式：`类型: 描述`，**禁止 scope**（`fix(api-doc)` 等），禁止 `Co-Authored-By` 等后缀，禁止自动 push。

禁止 `git add -A` / `git add .`，一律按文件清单逐个暂存。

## 流程

### 一、扫描

1. 候选范围 = 仓库所有改动文件（含未追踪新文件），忽略暂存状态
2. 执行 `git status && git diff HEAD`；未追踪新文件额外读取内容
3. 用户指定排除的文件，从候选范围中剔除

### 二、敏感检测

4. 扫描候选文件，匹配 `.env`、`credentials`、`*.pem`、`*.key`、`password`、`secret` 等
5. 命中则警告并列出清单，用户选择处理方式：
   - **纳入提交**：将该敏感文件归入"本次要提交的文件"
   - **忽略敏感文件**：将该敏感文件归入"忽略的文件"（排除出本次提交）

### 三、输出文件报告

6. 输出：

   ```
   ## 本次提交文件范围

   ### 本次要提交的文件
   - path/to/file1

   ### 忽略的文件
   - path/to/file2：原因
   ```

   - 空分组输出 `- 无`，不得省略分组
   - "本次要提交的文件"仅列路径；"忽略的文件"逐项注明原因
   - 当同一忽略原因覆盖某个目录下的全部候选文件时，"忽略的文件"只展示目录级别整体忽略，例如 `path/to/dir/：原因`，不要展开列出目录内每个文件
   - 敏感文件按用户选择归入对应分组，不单独成组

### 四、生成 commit message

7. 仅基于"本次要提交的文件"的 diff 和内容分析，确定类型（feat/fix/refactor/docs/style/test/chore）
8. 输出：

   ```
   类型: 总结性描述(一行)

   - 改动点（≤5个，按重要程度降序，说明"做了什么"）
   ```

### 五、确认&调整

9. 请求提交授权前，必须先在用户可见的普通消息中完整展示：
   - `## 本次提交文件范围`
   - `### 本次要提交的文件`
   - `### 忽略的文件`
   - 完整 commit message
10. 授权请求可以由执行模型自行选择形式，但无论使用工具确认、普通问题确认，还是其他交互形式，都必须发生在完整展示文件范围和 commit message 之后
11. 发起授权前必须自检：如果未展示提交文件范围、忽略文件范围或完整 commit message，禁止请求授权，必须先补充展示完整内容
12. 用户可能：**确认提交**、**调整提交范围**（忽略文件/将忽略文件加入提交）、**调整 message**、**取消提交**
13. 用户调整范围或 message → 回到**步骤三**重新输出；循环至确认或取消

### 六、提交

12. `git add` 要提交的文件 → `git reset` 忽略的文件 → `git commit -m "确认的 message"`

## Commit 类型

| 类型 | 说明 | 示例 |
|-----|------|------|
| feat | 新增功能 | `feat: 新增用户注册功能` |
| fix | 修复 bug | `fix: 修复登录验证重复问题` |
| refactor | 重构代码 | `refactor: 重构工具类方法` |
| docs | 文档变更 | `docs: 更新部署说明` |
| style | 代码格式 | `style: 格式化代码` |
| test | 测试相关 | `test: 新增用户服务单元测试` |
| chore | 构建/工具 | `chore: 升级依赖版本` |
