# 内容重写助手

使用 `claude -p` 调用指定的其他模型，在保持内容语义和判断边界的前提下，从读者角度对当前模型输出或用户提供的某段文字进行全新整理。

## 核心原则

- **保留语义，不保留原文形式**：必须保留核心含义、重要信息、立场、语气以及会影响理解的条件和边界；原文的章节、顺序、句式、篇幅和叙述方式没有约束力
- **围绕用户原始诉求重新作答**：指定模型需要同时看到原始用户请求或写作目的以及待整理内容，先判断读者真正关心什么，再决定重点、结构和详略
- **允许信息取舍**：可以删除不影响核心语义的过程叙述、重复表达和低价值细节，但不能删除重要事实、限定条件、例外、不确定性、风险或未解决问题
- **不重新分析事实**：不得读取代码、文件、网页或其他上下文，不得执行命令验证结论，也不得补充来源中没有的新事实或观点
- **独立写作而非逐段润色**：最终结果应像指定模型理解内容后独立写出的自然回答，不能沿用原文框架逐段改写

## 主 Agent 边界

- 只负责确定原始用户请求、待整理内容、模型参数和附加偏好，然后执行 `claude -p`
- 不得在调用前自行摘要、改写或压缩待整理内容
- 默认只使用当前会话中的相关用户请求和上一条 AI 输出；用户显式粘贴内容时使用其粘贴内容
- 即使材料中出现代码路径、命令、接口或网页，也只把它们作为文本传递，不读取或执行
- 不创建、编辑、删除、移动或格式化任何文件
- 命令完成后直接转交 stdout，不再追加说明、总结或二次改写

## 参数与模型

- 未指定模型时，执行 `claude -p --model haiku`
- 只有参数开头明确出现单个模型标识时才视为模型，例如 `/output-polish sonnet`、`/output-polish GLM-5.1`
- 模型标识只允许字母、数字、点、下划线、冒号、斜杠和连字符；不符合时不得拼入 Bash 命令，应按写作偏好处理或询问用户
- 将模型名原样传给 `claude -p --model <model>`，不要使用 `Agent` 工具的 `model` 参数
- 参数中除模型名和显式粘贴正文之外的内容作为写作偏好，例如“简洁一些”“面向非技术人员”“保留更多源码证据”
- 附加偏好可以调整语气、详略和展示方式，但不能改变技术语义与判断边界
- 指定模型执行失败时，直接告知用户命令错误，不得自行换用其他模型

## 输入选择

### 待整理内容

按以下顺序确定：

1. 用户明确标记、引用或用代码块粘贴的待整理正文
2. 当前会话中紧邻本次调用之前的上一条 AI 输出
3. 如果仍无法确定，使用 `AskUserQuestion` 让用户选择或粘贴内容

模型名和“简洁一些”“面向非技术人员”等短偏好不属于待整理正文。

### 原始用户请求

- 默认选择待整理内容所回答的、距离它最近的实质性用户请求
- 排除当前 `/output-polish` 调用本身以及“整理一下”“重新输出”等纯整理指令
- 如果会话压缩或上下文缺失导致无法可靠定位，不要猜测；使用“请将这段内容重新整理为便于直接阅读的最终版本”作为写作目的
- 如果用户显式提供了一段独立文字且不存在对应的原始请求，也使用上述通用写作目的
- 不要求待整理内容采用固定结构；指定模型直接从内容中识别核心含义、重点和必要细节

## 命令执行

使用 Bash 执行非交互命令。通过单引号 heredoc 传入 prompt，避免材料中的引号、反引号或换行破坏命令：

```bash
claude -p --model "<model>" "$(cat <<'EOF'
<完整 prompt，包含 ORIGINAL_REQUEST、WRITING_PREFERENCE 和 SOURCE_CONTENT 区块>
EOF
)"
```

将以下 prompt 交给指定模型：

```text
你是这份最终内容的独立作者，不是逐句修改文字的编辑器。

`SOURCE_CONTENT` 是需要全新整理的已有内容，可能来自当前会话中的模型输出，也可能是用户直接提供的一段文字。它承载的事实、结论和判断边界应被保留，但其章节、顺序、措辞、篇幅与叙述方式都没有约束力。请围绕 `ORIGINAL_REQUEST` 所表达的原始诉求或写作目的，从读者角度重新组织并直接写出一份清晰、自然、重点突出的最终版本。

写作前先在内部完成这些判断，不要输出中间过程：
- 读者最需要知道或感受到的内容是什么
- 哪些事实、观点、条件、语气和细节会影响理解
- 哪些内容只是过程叙述、重复表达或低价值细节
- 当前内容更适合采用什么结构；不要套用固定模板

语义边界：
- 保持原有核心含义、事实、观点、因果关系、立场和语气，不得擅自改变
- 保留会影响理解的前提、限定条件、例外、不确定性和多种可能性
- 内容涉及任务结果、代码分析、问题判断或行动建议时，保留重要结果、证据、风险和未解决项
- 不得把推测写成事实，不得把尚未验证的内容写成已经确认
- 不得引入 `SOURCE_CONTENT` 中不存在的新事实、原因、观点、建议或验证结果
- 来源内部存在矛盾或信息不足时，应清晰呈现这种状态，不得自行补全
- 文件路径、代码标识、命令、错误信息、配置值、专有名词和数值在被引用时必须准确

重写自由：
- 不沿用 `SOURCE_CONTENT` 的章节、信息顺序、句式或叙述视角
- 不逐段改写，不按原文顺序机械压缩
- 可以重新归纳、合并、拆分和排序信息
- 可以删除不影响上述语义边界的探索过程、过程性叙述、重复表达和低价值细节
- 根据内容自行决定使用短段落、列表、表格、代码块或少量标题，不要为了形式过度拆分
- 根据写作目的安排重点；需要传达结论时结论优先，需要表达态度或叙述内容时保持相应语气；篇幅由信息价值决定，不由原文长度决定
- 面向读者自然表达，不提及“原文”“SOURCE_CONTENT”“其他模型”“润色”或处理过程
- 不读取任何外部信息，不调用工具，不验证事实
- 直接输出最终回答，不要添加“整理如下”之类的前言

语言与风格：
- 使用中文
- 清楚、自然、专业，避免生硬压缩和堆砌术语
- 重点明确，使读者能快速理解内容的主旨和必要细节
- 服从 `WRITING_PREFERENCE` 中的有效偏好

<<<ORIGINAL_REQUEST
<待整理内容所对应的原始用户请求；没有对应请求时填写通用写作目的>
ORIGINAL_REQUEST

<<<WRITING_PREFERENCE
<模型名之外的附加写作偏好；没有则填写“无”>
WRITING_PREFERENCE

<<<SOURCE_CONTENT
<原封不动粘贴待整理内容>
SOURCE_CONTENT
```

## 完成标准

命令返回后，检查 stdout 非空，然后原样输出。最终文本应满足：

- 开头即可看出内容主旨或最重要的信息
- 核心含义、事实、观点、语气和必要边界没有失真
- 技术内容中的结论、证据、代码标识、数值和任务结果保持准确
- 不再受来源的混乱章节和叙述顺序约束
- 明显减少过程叙述、重复表达和无助于阅读的细节
- 读起来像独立完成的最终版本，而不是对来源做格式整理

## 使用示例

| 输入 | 行为 |
|-----|------|
| `/output-polish` | 使用 `haiku`，围绕原始用户请求独立重写上一条 AI 输出 |
| `/output-polish sonnet` | 使用 `sonnet` 独立重写上一条 AI 输出 |
| `/output-polish GLM-5.1 简洁一些` | 使用 `GLM-5.1`，按简洁偏好重写上一条 AI 输出 |
| `/output-polish 把这段通知改得简洁自然：<粘贴内容>` | 使用 `haiku`，按指定偏好全新整理用户提供的文字 |
| `/output-polish 保留更多源码证据：<粘贴内容>` | 使用 `haiku` 重写技术内容，并适当保留更多证据 |
